# Frontend Audit — 2026-09-09

Read-only investigation ahead of the internal dry run. Nothing in the codebase was changed to produce this document. Priority framing per the request: **the app must never leave a distributor stuck** — a crash or dropped connection mid-recording or mid-upload must be recoverable by simply reopening the app.

---

## 1. ERROR STATES

| State | Status | Where |
|---|---|---|
| Camera/mic permission denied (initial ask) | **Handled** | `PermissionsScreen.tsx:55-100` (guided denied-state with numbered Settings steps), `CameraAlignment.tsx:435-470` (in-camera fallback with retry/Settings) |
| Camera/mic permission revoked mid-session (live, while recording) | **Not handled** | No live listener during an active take. `CameraAlignment.tsx:435` re-renders into the permission-fallback UI reactively once `hasCamera`/`hasMic` flip false (vision-camera's hooks do react to this), but that render swap happens underneath whatever `phase` AppFlow is in — including `recording`. It does not call `onRecordingError`, does not stop the recorder, and does not update `AppFlow`'s `phase`. In practice a live mid-take revoke is a rare OS-level edge case on Android (usually requires backgrounding first), but the code path has no explicit handling if it does happen. |
| Storage full before recording | **Not handled** | No disk-space check anywhere in the repo (confirmed via repo-wide search — no `diskSpace`/`freeDiskStorage`/`ENOSPC` reference exists). Recording is allowed to start unconditionally. |
| Storage full during recording | **Not handled** (surfaces as a silent dead end) | A native write failure would reach `onRecordingError` (`CameraAlignment.tsx:412`), which `AppFlow.tsx:1712` wires to `console.error` only — no state change, no user-facing message. See CRASH RESILIENCE §3 for the full consequence chain. |
| Battery critically low | **Not handled** | No battery-level check anywhere in the repo. |
| Server unreachable — question fetch | **Handled** | `AppFlow.tsx`'s `loadQuestions()` (~L379-404) is cache-first: shows cached questions immediately, keeps them on a failed refetch, and only sets `questionsError` when there is truly nothing cached. Rendered with a retry button at `AppFlow.tsx:1379-1397`. |
| Server unreachable — My Videos fetch | **Handled** | `myVideosError` state, set in the try/catch around `Promise.all([fetchSegments(), ...])` (~L753-866 in the pre-audit read), passed through as `error` and rendered by `MyVideosScreen.tsx:108-112`. |
| Server unreachable — upload | **Partially handled** | `api.ts:58-60` converts a fetch failure into `ApiError(0, 'network_error', ...)`. The upload loop (`AppFlow.tsx:704-720`) catches it, sets `uploadError`, and stops — `UploadingScreen.tsx:60-72` shows "Try again" (resumes correctly, see §2) and "Send later." Reasonable, but the shown message is whatever `error.message` happens to be (a raw `ApiError`/`Error` string), not a curated "no connection" copy distinguishing network vs. server-side failure. |
| Session/auth token expired mid-flow | **Not handled well** | `auth.ts` has no refresh mechanism at all — a token is valid until its ~30-day expiry or a backend-side revoke, with no renewal path. A 401 mid-flow (e.g. mid-upload) surfaces as a generic `ApiError` and is displayed as plain error text via whatever call site catches it (e.g. `uploadError` on the Uploading screen) — there is no detection of "this is specifically an auth failure," no automatic redirect to `login`, and no clearing of the now-dead token. A distributor would see a confusing upload-failure message and have no obvious path to re-authenticate short of manually finding Logout in Profile. |
| Back button pressed mid-recording | **Handled well** | `AppFlow.tsx`'s hardware-back handler (~L631-650) sets `pendingExitConfirm` for `cameraCheck`/`countdown`/`recording`/`reviewTrim` rather than exiting silently; `confirmExitQuestionFlow()` (`AppFlow.tsx:1122`) calls `cameraRef.current?.cancelRecording()` when `phase === 'recording'` before routing back to `brief`. This is one of the better-handled states in the app. |
| Recording that's empty or too short | **Not handled** | `handleRecordingFinished` (`AppFlow.tsx:940`) computes `durationSeconds` from a wall-clock timestamp diff and accepts it unconditionally — no minimum-duration floor, no check for `durationSeconds <= 0`. A near-instant tap of "I'm done answering" produces a take that flows straight into Review & Trim with no warning. |
| Phone call / other app taking the mic mid-recording | **Not handled** | No `AppState` listener exists anywhere in the recording path (confirmed by repo-wide search — the only `AppState`-adjacent behavior is vision-camera's own internal permission-hook refresh, unrelated to audio focus). If a call/interruption causes a native recording error, it routes through the same silent `onRecordingError → console.error` dead end described above. If it doesn't error and the OS just resumes the session afterward, there is no detection that a gap occurred either. |

### Other error states found, not on the original list

- **`ApiError` message trust**: `api.ts:68` surfaces the backend's own `message` field directly to the user (or a hardcoded `'Something went wrong.'`/`'Upload failed.'` fallback) with no per-error-code UI mapping anywhere in the app except the one specific `phone_already_registered` case. Every other backend error code (auth, validation, rate-limit, etc.) reaches the user as raw backend prose or a generic fallback — functional, but not designed error copy.
- **`EXPO_PUBLIC_API_BASE_URL` unset**: `api.ts:37-41` throws a developer-facing error string ("check .env.local and restart the dev server") — correctly impossible in a real build (inlined at build time), but worth confirming that env var is actually baked into the dry-run build before shipping it, since there's no runtime fallback if it somehow isn't.
- **Question set changed under a stale local recording**: `upload.ts:54-57` throws `upload.questionSetChanged` if `questions[video.questionIndex]` doesn't exist (backend's question list shrank/reordered since the video was recorded). This stops that segment's upload with a clear error but — per the upload loop's `return` on first error (`AppFlow.tsx:701-722`) — also silently stops uploading every segment after it in the batch, not just the affected one. See §2.

## 2. UPLOAD RELIABILITY

**Trace**: `AppFlow.tsx`'s upload effect (`~L685-733`) → `uploadSegment()` (`upload.ts:49-105`) → `putVideoBytes()` (`upload.ts:27-33`, `expo-file-system`'s `File.upload()`) → `POST /segments/confirm`.

- **Resume after a network drop**: **Restarts from zero, at the segment level, not the byte level.** `putVideoBytes` uses `expo-file-system`'s `File.upload()` — a single native PUT of the whole file to the presigned URL, with no chunking or byte-offset resume API in play (confirmed: no `tus` client, no `react-native-background-upload` in `package.json`, despite `CLAUDE.md`'s original decision calling for exactly that). If the PUT is interrupted, the promise rejects and the entire file must be re-sent from byte 0 on retry. What *is* granular is which **segments** get retried: the loop skips any `questionIndex` already in `uploadedQuestionIndices` (`AppFlow.tsx:709`), so a batch of 5 doesn't restart entirely — only the segment that failed (and anything after it, since the loop `return`s on first error) gets re-attempted from scratch.
- **Resume if backgrounded or killed mid-upload**: **No true background upload.** There is no native background-transfer mechanism (no iOS `URLSession` background config, no Android `WorkManager`) — the upload runs only while the JS engine is alive and the effect is mounted. If the app is *killed*, the in-flight PUT dies with the process; on next launch, `restoreSession()`/`loadSession()` restores `uploadConfirmed: true` (guarded — see `AppFlow.tsx:551-568`'s comment on the persistence-loop bug already fixed for this exact scenario) and the upload effect re-fires, correctly resuming from the first segment not yet in `uploadedQuestionIndices`. So **a killed app resumes correctly on relaunch** — the gap is specifically *while backgrounded but not killed*: Android's battery/Doze management on the budget/mid-range hardware this app targets (per `CLAUDE.md`) can suspend network activity for a backgrounded app well before the OS actually kills the process, silently stalling an in-flight PUT with no user-visible signal and no automatic resume until the app is foregrounded again.
- **Duplicate-upload risk on retry**: **Yes, a real risk exists**, specific to the case where a PUT actually lands in S3 but the client never receives the `/segments/confirm` response (e.g. response lost to a network drop after the request succeeded server-side). On retry, `uploadSegment()` runs the full sequence again from scratch — new presigned URL, new S3 object under a new `video_key`, a second `POST /segments/confirm` for the same `question_index`. Whether this creates a duplicate segment record (and duplicate wasted storage / duplicate render trigger) depends entirely on backend idempotency, which the frontend has no visibility into and cannot fix alone (see §5). Separately, `uploadSegment`'s own internal retry-on-`video_not_found` (`upload.ts:97-104`) is deliberately safe by design — that code specifically means the original PUT never landed, so redoing it is correct, not a duplicate.
- **Progress accuracy**: Accurate at segment granularity — `uploadProgress` is `uploadedQuestionIndices.length / primaryVideos.length` (`AppFlow.tsx`, derived effect near the upload loop), recomputed the instant a segment confirms. It does **not** reflect in-flight byte progress of the segment currently uploading (e.g. a 5-question batch sitting at 60MB into a 100MB file 3-of-5-through still shows the same "2 of 5" / 40% until that segment fully confirms) — coarse but not misleading.
- **Cancel**: **Not actually wired.** `ConfirmationScreen.tsx`'s only button is "Back to Home" (`onDone`), and per `AppFlow.tsx`'s own comment on the upload effect (~L679-684), navigating away deliberately does **not** tear down the effect — the upload continues in the background regardless of what screen is showing. There is no button anywhere that stops an in-flight confirmed upload. This is a defensible product choice (matches "release and forget" framing, and avoids a half-sent batch from an accidental tap) but it means "cancel" as literally requested doesn't exist as a user action once a batch is confirmed.

## 3. CRASH RESILIENCE

### Native-module boundaries

| Boundary | Wrapped? | Where |
|---|---|---|
| `expo-audio` `AudioRecorder` (ambient noise check) | **Yes, thoroughly** | `useAmbientNoiseCheck.ts` — every native call (`stop()`, `prepareToRecordAsync()`, `getStatus()`) is in try/catch, including a documented case (`safeStop`, L69-78) for a *synchronous* throw that a bare `.catch()` wouldn't protect against. This file is the gold-standard pattern in the codebase — see `DEV_NOTES.md`'s own resolved-investigation writeup for the incident that produced it. |
| `expo-video` player (Camera Check screen's VO playback) | **Yes** | `CameraCheckScreen.tsx:79-107` (`safePause`), same released-object pattern as above, explicitly documented as deliberately copied from `useAmbientNoiseCheck.ts`. |
| `expo-video` player (My Videos / finished-take playback) | **Yes** | `VideoPlayerScreen.tsx:48-65` — try/catch around player calls. |
| `expo-video` player (Review & Trim preview) | **No — inconsistent with the two screens above** | `ReviewTrimScreen.tsx:84-86`: `useVideoPlayer(selected?.filePath ?? null, (p) => { p.pause(); })` — the setup callback's `p.pause()` is bare, no try/catch, unlike the other two `expo-video` call sites in this app that learned this exact lesson. Switching the previewed take rapidly (tapping between take rows) is the closest analog to the CameraCheckScreen crash trigger (a player recreated/released while a callback is still in flight) — this hasn't been reported as crashing yet, but it's the one `expo-video` site in the app that doesn't follow the pattern the rest of the codebase already treats as mandatory. |
| `react-native-vision-camera` `Recorder` (start/stop/cancel) | **Partially** | `startRecording`/`stopRecording`/`cancelRecording` (`CameraAlignment.tsx:386-421`) are exposed as async functions and every call site (`AppFlow.tsx`) wraps them in `.catch(console.error)` — so a rejected promise won't crash the app. But a **recording error reported via the native callback** (`onRecordingError`, the second callback passed to `recorder.startRecording()`, `CameraAlignment.tsx:412`) is a different path — see below, this is the real gap. |
| `react-native-vision-camera-face-detector` | **Yes** | `onError: (error) => console.error(...)` at `CameraAlignment.tsx:327` — non-fatal by design, detection just stops producing frames. |

### The `onRecordingError` gap — most important finding in this audit

`AppFlow.tsx:1712`:
```
onRecordingError={(error) => console.error('[recording]', error)}
```
This is the **entire** handling for a native recording failure — no state change, no navigation, no user-facing message. Trace what a distributor actually experiences if this fires mid-take (storage full, camera session torn down, hardware fault, mic taken by another app):

1. `phase` stays `'recording'`. The on-screen timer (`AppFlow.tsx`'s `elapsedSeconds` ticker) is a plain `setInterval` unrelated to the actual native recording state, so it **keeps counting up** — nothing on screen indicates anything is wrong.
2. The distributor, seeing what looks like a normal recording in progress, eventually taps "I'm done answering" → `onFinishAnswer` → `cameraRef.current?.stopRecording()` (`AppFlow.tsx:1750-1752`) → `recorderRef.current?.stopRecording()` (`CameraAlignment.tsx:416`). Since nothing cleared `recorderRef.current` when the error fired, this either silently no-ops or rejects into another `.catch(console.error)`.
3. Critically, **`onRecordingFinished` never fires** in this scenario (it's only invoked by the native recorder's own success callback) — so `handleRecordingFinished` (`AppFlow.tsx:940`) never runs, `phase` never advances to `reviewTrim`, and nothing is added to `takesByQuestion`.
4. **The distributor is now stuck on the Recording screen indefinitely, with zero on-screen indication anything failed**, and no automatic way forward. The only actual recovery path is the hardware/gesture back button (which *is* handled correctly — `confirmExitQuestionFlow` calls `cancelRecording()` and returns to `brief`) — but nothing on screen tells a non-technical user that's what they need to do. Most people in this situation will assume the app is frozen, not that a "go back" gesture will fix it.

This directly contradicts the audit's stated top priority: a mid-recording failure is not currently a "reopen the app and continue" situation — it's a silent, undiscoverable freeze whose only escape is a hardware button with no on-screen prompt.

### Force-quit / relaunch recovery (the "reopen the app" case specifically)

Traced precisely, not assumed, against `session.ts` and `AppFlow.tsx`'s restore effect (~L418-518):

- **Mid-recording or mid-countdown force-quit**: `restorableQuestionPhase()` (`session.ts:100-103`) deliberately maps both `'countdown'` and `'recording'` back to `'brief'` on restore — correct, since (per that function's own comment) a take is never added to any restorable state until `onRecordingFinished` actually runs, so there's nothing to resume *into*. `purgeOrphanedRecordingTempFiles()` (`session.ts:126-138`, called from the restore effect when `stored.phase` was `'recording'`/`'countdown'`) cleans up the actual orphaned temp file on Android (the equivalent iOS temp file can't be positively located from JS, but is documented as OS-purged on next launch — see that function's own comment for the reasoning). **Net result: nothing is lost except the interrupted take itself** (never existed as a keepable asset), and the person lands back on the Question Brief for the same question, matching a deliberate cancel. This is well-handled.
- **Mid-review-trim force-quit**: Restored back into `reviewTrim` if there's still a live take to review; if a force-quit happened in the narrow window right after `handleKeepTake` finalized the take but before the post-keep popup was dismissed (`reviewTrimWithNothingToReview`, restore effect ~L488-490), it correctly lands on Home instead of reopening an empty picker — the take itself is safe either way since `handleKeepTake` already moved it into `videos` before that window.
- **Mid-upload force-quit**: As covered in §2, resumes correctly via `uploadedQuestionIndices` + the `uploadConfirmed` persistence guard.
- **Question set shrank/reordered while a session was mid-flight**: `questionIndexStillValid` check (restore effect ~L499-500) — if the restored `questionIndex` no longer exists in the (synchronously known, cached) question set, routes to Home rather than a broken/out-of-range question screen. Handled.

### Global error boundary

**None exists.** `App.tsx` is a flat tree (`SafeAreaProvider` → `ThemeProvider` → `AppFlow` + a few chrome siblings) with no `ErrorBoundary`/`componentDidCatch`/`getDerivedStateFromError` anywhere in the repo (confirmed by a repo-wide search — zero matches). **Any uncaught exception thrown during render, anywhere in this ~1,800-line `AppFlow.tsx` state machine or any screen it renders, will crash the entire app** — not just fail to render one screen. Given `AppFlow.tsx` is one large component handling permissions, camera, upload, session restore, and navigation all in one render function, the blast radius of a single uncaught error is the whole app, with no fallback UI, no "something went wrong, here's a way back" screen, and no crash telemetry visible in this codebase (no Sentry/Bugsnag/crash-reporting SDK found either — meaning a crash in the field during the dry run would leave you with zero visibility into what happened beyond whatever the distributor can describe).

## 4. GAPS AND RISK

Ranked by estimated likelihood of actually happening across ~15-20 non-technical distributors on a range of Android phones during a real dry run, not by theoretical severity alone.

1. **No global error boundary (§3).** With ~20 real users on varied hardware exercising camera/upload/session-restore code all in one unguarded render tree, *some* uncaught edge case is likely, and today that means a full app crash with no recovery screen, not a contained failure. This is the highest-leverage single fix available — it doesn't prevent bugs, but it turns "app is dead, reinstall or give up" into "one screen broke, here's a way back," which is the actual stated priority.
2. **The `onRecordingError` silent-freeze (§3).** This is a near-certain occurrence, not a rare edge case, at this device range — MediaTek/Unisoc budget chips are explicitly called out in this codebase's own comments (`CameraAlignment.tsx:387-389`) as a source of quirky native encoder behavior. Any native recording hiccup on any of these ~20 phones currently produces an undiscoverable frozen screen instead of a message + retry. This is cheap to fix (the state and navigation machinery already exists — `pendingExitConfirm`/`confirmExitQuestionFlow` already does the right recovery, it's just not triggered automatically) and should be prioritized alongside the error boundary.
3. **No minimum-recording-duration check (§1).** With non-technical users, an accidental near-instant tap of "I'm done answering" (fat-finger, confusion about the flow, a false start) is plausible and currently produces a valid-looking but empty/near-empty take with no warning, silently degrading what gets reviewed/uploaded.
4. **Real background/backgrounded-app upload stalls (§2).** Given the explicit "patchy tier-2/3 network" context this app is built for, someone switching apps mid-upload (to check WhatsApp, take a call, etc.) on an aggressive-battery-management Android phone is a realistic, not edge-case, scenario — and today it silently stalls with no background transfer and no user-visible signal until they return to the app.
5. **Token-expiry mid-flow (§1) and the possible duplicate-upload risk (§2).** Lower likelihood specifically during a short dry run (30-day token lifetime, and duplicate-upload requires a fairly precise network-drop timing), but worth having answers ready for since both trace back to backend behavior this audit can't verify from the frontend alone (see §5).

## 5. NEEDS FROM BACKEND

- **Idempotent `/segments/confirm`.** The frontend cannot rule out duplicate segment records on a retry after a "PUT succeeded, confirm response lost" scenario (§2) without knowing whether the backend treats a repeated `(question_index, video_key)` confirm as an upsert or a fresh insert. If it's not already idempotent per `question_index`, this needs a backend-side change (or an explicit idempotency key the frontend can generate and pass) — the frontend has no way to detect "did my previous confirm actually land" after a network error, since the error itself is exactly the ambiguous case.
- **A way to check upload status after a crash/reinstall**, independent of local session state. Today the frontend's only source of truth for "what's already uploaded" after a force-quit is its own locally-persisted `uploadedQuestionIndices` (`session.ts`) plus a full `GET /distributors/me/segments` refetch once on the My Videos tab. If local storage itself is lost (app data cleared, reinstall, new device), there's no reconciliation step that checks the server before deciding what still needs recording/uploading — a distributor who reinstalls mid-batch would currently have no way to know their earlier segments already made it to the server without manually checking My Videos first.
- **Distinguishable error codes for auth failure vs. other 401/403s.** Right now `ApiError.code` is whatever string the backend sends (`api.ts:68`); the frontend has no explicit handling that says "this specific code means the token is dead, force a re-login" — worth confirming the backend actually sends a distinct, documented code for expired/revoked-token responses (vs. e.g. a generic `unauthorized`) so the frontend can build that handling rather than showing a generic upload-failed message when the real cause is auth.
- **Token refresh, or at minimum a longer/renewable session**, if a 30-day flat expiry with no refresh path is intentional — worth confirming that's still the desired tradeoff, since it means any distributor whose token expires mid-batch (unlikely in a short dry run, more relevant post-launch) has no graceful recovery today, just a confusing failed upload.
- **Clear, mappable error codes generally.** Beyond auth, `api.ts` passes the backend's raw `message` straight to the user for every error code except `phone_already_registered` and `video_not_found`, both of which get special frontend handling specifically because they're documented, known codes. Any other backend error (validation failures, rate limits, server-side storage issues) surfaces as whatever prose the backend happens to send, unreviewed for whether it's something a non-technical distributor would understand. A documented, stable set of error codes (even a short list) would let the frontend build real copy for the most common ones instead of showing raw backend messages.
